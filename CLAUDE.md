# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Responde al usuario en español.

## Objetivo

Aplicación tipo Comunio para la primera división española (LaLiga). Estado: el juego está completo en backend y web (cuentas con verificación de email, ligas privadas, plantillas, tácticas, mercado, ofertas, dos modos de avance de jornada y clasificación) sobre la temporada **2024/25**: equipos, plantillas y calendario son reales (API-Football) y las actuaciones de los jugadores se **simulan** (paquete `simulacion`), lo que permite jugar las 38 jornadas sin plan de pago. Los valores de mercado salen del archivo de Biwenger y, para quien no aparezca en él, se generan.

`README.md` (en la raíz) es la documentación de cara al usuario: cómo se juega, de dónde salen los datos y cómo arrancarlo. Este archivo es el detalle técnico y las decisiones ya tomadas.

**La app móvil está aparcada**: la plataforma Android existe en `frontend/android/` y funciona, pero no se mantiene; queda para una actualización futura. No dediques trabajo a Capacitor salvo que se pida.

## Estructura

Monorepo con tres partes:

- `backend/` — Spring Boot **3.5** (Java 21, Maven con `mvnw`), Spring Data JPA, PostgreSQL, Actuator, Validation, Lombok. Paquete base `com.ligacomunio`.
- `frontend/` — React 19 + TypeScript + Vite, linter oxlint. Móvil con **Capacitor** (`capacitor.config.ts`, `webDir: dist`): una sola base de código web empaquetada como app nativa.
- `docker-compose.yml` — entorno de desarrollo: `db` (Postgres 16), `backend` (`mvn spring-boot:run` con código montado), `frontend` (Vite dev server).

## Comandos

Entorno completo (requiere Docker): `docker compose up --build` → frontend en :5173, backend en :8080, Postgres en :5432.

Backend (desde `backend/`):
- `./mvnw spring-boot:run` — arrancar (necesita Postgres accesible; por defecto `localhost:5432/ligacomunio`, usuario/clave `ligacomunio`).
- `./mvnw -DskipTests package` — compilar.
- `./mvnw test` / `./mvnw test -Dtest=NombreTest#metodo` — todos los tests / uno solo. `BackendApplicationTests` (contextLoads) necesita una BD disponible.

Frontend (desde `frontend/`):
- `npm run dev`, `npm run build` (tsc + vite), `npm run lint`.
- Móvil (Android): la plataforma está generada en `frontend/android/` (iOS no: no se puede compilar desde Windows). `npm run build:android` construye con `.env.android` (`VITE_API_URL`: IP del PC en la Wi-Fi para un móvil real, `http://10.0.2.2:8080` para el emulador) y `npm run android` además sincroniza y abre Android Studio. En desarrollo `capacitor.config.ts` usa `androidScheme: 'http'` (origen `http://localhost`, ya permitido en CORS) y el manifest lleva `usesCleartextTraffic="true"`; **al publicar con HTTPS hay que quitar ambos**. Un móvil real necesita que el firewall de Windows deje entrar el puerto 8080. Hay que ejecutar `npm run build:android` y `npx cap sync android` cada vez que cambie el código web, y también al añadir un plugin de Capacitor (`@capacitor/preferences`, que guarda la sesión en nativo) para que se instale su parte nativa en `frontend/android/`.

## Arquitectura / convenciones

- La configuración del backend se parametriza por variables de entorno (`DB_URL`, `DB_USER`, `DB_PASSWORD`, `CORS_ALLOWED_ORIGINS`) con valores por defecto de desarrollo en `application.properties`.
- El frontend llama al backend con rutas relativas (`/api`, `/actuator`); en desarrollo Vite las proxifica a `BACKEND_URL`. En la app Capacitor no hay proxy (el origen es `capacitor://localhost` / `http://localhost`), así que habrá que configurar una URL base de API para builds móviles; el CORS del backend ya admite esos orígenes para `/api/**`.
- Spring Initializr ya solo ofrece Boot 4.x: el `pom.xml` se bajó a mano a 3.5.x (starters `-web` y `-test`). No migrar a 4.x sin que se pida.
- Esquema gestionado con **Flyway** (`backend/src/main/resources/db/migration`, `V<n>__nombre.sql`); Hibernate solo valida (`ddl-auto=validate`). Cualquier cambio de entidades requiere una migración nueva; nunca editar una ya aplicada. `V2` y `V3` fueron datos de demo (equipos 2025/26 y 8 jugadores) y `V5` los elimina; no los reintroduzcas.
- Modelo: `Team`, `Player` (posición PORTERO/DEFENSA/CENTROCAMPISTA/DELANTERO), `Match` (tabla `matches`, `match` es palabra reservada-ish) y `PlayerMatchStats` (datos brutos por jugador y partido + `points` + `rating` opcional). Paquetes por dominio: `team`, `player`, `match`, `scoring`.
- Puntuación: `scoring/ScoringService` calcula los puntos desde `PlayerMatchStats` según la posición (minutos, goles, asistencias, entradas ganadas, tarjetas, % de pases acertados; porteros: paradas, goles encajados, tiros recibidos, minutos). Todos los pesos viven en ese único archivo y son una propuesta ajustable; los tests (`ScoringServiceTest`) no necesitan BD.
- API REST de lectura: `GET /api/teams[/{id}]` y `GET /api/players[/{id}]` (filtros `teamId`, `position`). Los controladores devuelven DTOs (`TeamDto`, `PlayerDto`), nunca entidades. `open-in-view` está desactivado, así que las consultas que devuelven `Player` deben hacer `join fetch` del equipo (ver `PlayerRepository.buscar`). Los tests de controladores usan `@WebMvcTest` + `@MockitoBean` (sin BD); la consulta real solo se verifica contra Postgres.
- Partidos y estadísticas (`match/`): `GET/POST /api/matches`, `GET /api/matches/{id}`, `PUT /api/matches/{id}/result`, y `GET/PUT /api/matches/{id}/stats`. El `PUT .../stats` hace upsert por (jugador, partido), exige que el jugador sea de uno de los dos equipos y **calcula `points` con `ScoringService`** (el cliente nunca envía puntos). Valida con `@Valid` (400) y la lógica vive en `MatchService`. Hoy los datos se cargan a mano por la API; la importación real irá detrás de una interfaz `StatsProvider`.
- Importación de datos reales (`importacion/`): interfaz `StatsProvider` (tipos neutros `EquipoExterno`, `PartidoExterno`, `EstadisticaExterna`) con una única implementación, `ApiFootballProvider` (API-Football v3, liga 140). `ApiFootballMapper` traduce el JSON; `ImportService` orquesta llamando a la API **sin transacción** y `GuardadoImportacion` persiste con transacciones cortas y calcula los puntos con `ScoringService`. Equipos, jugadores y partidos se emparejan por `external_id` (reimportar no duplica); los jugadores se crean al importar las estadísticas del partido en que juegan.
- Disparadores (solo `ADMIN`, ver Seguridad): `POST /api/admin/import/teams?season=2024`, `.../squads?season=2024`, `.../fixtures?season=2024`, `.../matchdays/{jornada}?season=2024&max=10`. Orden obligatorio: equipos → plantillas → calendario (las jornadas con estadísticas reales son opcionales: lo normal es simular). Una jornada importada tarda ~1 min (10 peticiones, espaciadas 6,5 s).
- **Plantillas completas** (`importarPlantillas`, `StatsProvider.plantillas`): usa `/players?league=140&season=X&page=N`, una petición por página de 20 (unas 30 para toda LaLiga), y **no** `/players/squads`, que solo da la plantilla actual sin poder pedir temporada. De cada jugador se toma la entrada de `statistics` del equipo en el que más partidos jugó. Así el catálogo está completo antes de jugar nada, en vez de ir creando jugadores a medida que aparecen en los partidos. Tras guardarlas se reaplican los valores de Biwenger y se **generan** los que falten (`GeneradorDeValores`, valor estable deducido del `external_id` y la posición, múltiplo de 50.000): un jugador sin valor queda fuera del juego, así que esto es lo que hace fichable a toda la liga. Si después aparece su precio real en Biwenger, ese manda.
- **Cuota de API-Football (plan Free):** 100 peticiones/día y 10/min; **solo temporadas 2022-2024** (2025 y 2026 dan error de plan). 1 petición por partido para estadísticas, 1 para equipos y 1 para el calendario. El proveedor consulta `/status` al empezar, descuenta cada petición y se detiene (429) al quedar ≤3. La clave va en `.env` (`API_FOOTBALL_KEY`, ignorado por git; plantilla `.env.example`); tras cambiarla, `docker compose up -d backend`.
- Mapeo de estadísticas: `tackles.total` -> entradas; `passes.accuracy` es el **número** de pases acertados (fallados = total − acertados); **tiros fallados = tiros totales − goles** (decisión del usuario); para porteros, tiros recibidos = paradas + goles encajados (la API no lo da); los `null` son 0; los suplentes sin minutos se descartan. `games.rating` se guarda en `rating`.
- Los datos de demo (`V2`, `V3`) se borraron con `V5`: equipos y jugadores salen ahora solo de la importación. Los jugadores importados tienen `market_value = 0` (la API no da valor de mercado; pendiente de decidir de dónde sale).
- **Autenticación** (`auth/`, `user/`, `config/`): usuarios en `app_user` (email en minúsculas, username único sin distinguir mayúsculas, bcrypt, rol `USER`/`ADMIN`). `POST /api/auth/register|login|refresh|logout` (públicos) y `GET /api/auth/me`. Access token = JWT HS256 de 15 min firmado con `JWT_SECRET` (claims `sub`=id, `role`); refresh token = aleatorio opaco de 30 días, guardado **solo como SHA-256** en `refresh_token`, con **rotación** en cada refresh y, si se reutiliza uno ya revocado, se revocan todos los del usuario (`AuthService.renovar` usa `noRollbackFor` para que esa revocación se confirme pese al 401). El login devuelve el mismo 401 "Credenciales incorrectas" para email inexistente y contraseña errónea.
- **Límite de intentos** (`auth/ControlDeIntentos`): tras `app.auth.max-intentos` fallos seguidos (5) se responde **429** con el tiempo que falta, durante `app.auth.bloqueo-segundos` (15 min); el contador se olvida solo pasada `app.auth.ventana-segundos` sin fallar y un login correcto lo borra (`exito`). Se cuenta por **email y por IP** a la vez (claves `login:email:...` / `login:ip:...`), así que el 429 puede venir de cualquiera de las dos. Los dos endpoints que mandan correo a una dirección elegida por quien llama (`/verify/resend` y `/password/forgot`) pasan por el mismo freno (`AuthController.limitarEnvios`, claves `resend:`/`forgot:`) para que no sirvan para inundar un buzón ajeno. El estado vive **en memoria**: con varias instancias del backend cada una contaría por su cuenta (habría que llevarlo a Redis).
- **Verificación de email y contraseña olvidada** (`auth/CuentaService`, `UserToken`, migración `V10`): `app_user.email_verified` y la tabla `user_token` (tipo `VERIFICACION`/`RESET`, hash **SHA-256**, un solo uso, caducidad; emitir uno gasta los anteriores del mismo tipo). Endpoints públicos `POST /api/auth/verify`, `/verify/resend`, `/password/forgot`, `/password/reset` (204 sin cuerpo). El registro manda el correo de verificación **fuera de la transacción**. `forgot` y `resend` responden 204 exista o no la cuenta (no deben revelar quién está registrado) y un token inexistente, usado o caducado da **el mismo 400** ("El enlace no es válido o ha caducado"). Restablecer la contraseña da la cuenta por verificada y **revoca todos los refresh token** del usuario. Con `app.auth.exigir-email-verificado=true` el login de una cuenta sin confirmar devuelve **403** (la contraseña correcta limpia igualmente el contador de intentos). `auth/Mailer`: si `spring.mail.host` está vacío **no envía nada y escribe el correo entero en el log** (así se prueba el flujo sin SMTP); nunca propaga un fallo de envío. `auth/LimpiezaDeTokens` (`@Scheduled`, `app.auth.limpieza-delay-ms`) borra refresh tokens y tokens de correo caducados (con 7 días de margen) y limpia el mapa de intentos.
- **Seguridad** (`config/SecurityConfig`): API sin estado, CSRF desactivado (token en cabecera, sin cookies), CORS vía `CorsConfig`. Públicos: `/api/auth/register|login|refresh|logout`, `/api/auth/verify`, `/api/auth/verify/resend`, `/api/auth/password/forgot`, `/api/auth/password/reset`, `/actuator/health` y `/error`. `/api/admin/**` exige `ROLE_ADMIN`; todo lo demás, estar autenticado. **`/error` debe seguir siendo público**: si no, los errores 400/404/409 llegan como 401. Añade cabeceras HSTS, `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff` y `Referrer-Policy: no-referrer`. `ApiExceptionHandler` devuelve `{"message": ...}` (y `errors` por campo en validaciones) solo para `ResponseStatusException` y validación; el frontend muestra esos mensajes.
- **Variables obligatorias/nuevas** (en `.env`, plantilla `.env.example`): `JWT_SECRET` (≥32 caracteres; el backend **no arranca** sin ella, y `docker compose` falla si falta), `ADMIN_EMAIL` y `ADMIN_PASSWORD` (8-72 caracteres; si ambas están rellenas se crea ese ADMIN al arrancar si no existe — así se crea el primer administrador). El rol va dentro del token: un cambio de rol solo se nota al volver a iniciar sesión. Para el correo: `MAIL_HOST`, `MAIL_PORT` (587), `MAIL_USER`, `MAIL_PASSWORD`, `MAIL_FROM`, `FRONTEND_URL` (base de los enlaces del correo, sin barra final) y `EXIGIR_EMAIL_VERIFICADO` (**false** mientras no haya SMTP: sin `MAIL_HOST` el enlace solo sale por el log y quien se registrase se quedaría fuera). Todas se pasan al servicio `backend` en `docker-compose.yml`.
- Tests de controladores con `@WebMvcTest` llevan `@AutoConfigureMockMvc(addFilters = false)` para no depender de la seguridad; las reglas de acceso se prueban en `SecurityConfigTest`, que importa `SecurityConfig` y `JwtConfig`, firma tokens reales y comprueba que las cuatro rutas del correo son públicas y que salen las cabeceras de seguridad. `ControlDeIntentosTest` y `CuentaServiceTest` son de memoria pura (sin BD ni contexto de Spring); `AuthServiceTest` cubre el 429 y el reinicio del contador tras un login correcto.
- **Pendiente de seguridad**:
  - **HTTPS antes de publicar.** `server.forward-headers-strategy=framework` ya está puesto para funcionar detrás de un proxy TLS (respeta `X-Forwarded-*`, así que el control de intentos ve la IP real). Al publicar hay que quitar `usesCleartextTraffic="true"` del manifest de Android y `androidScheme: 'http'` de `capacitor.config.ts`, y poner `FRONTEND_URL` con el dominio real (los enlaces del correo salen de ahí).
  - **Cifrado real del token en el móvil**: hoy va en `Preferences` (`SharedPreferences`, privado de la app pero **sin cifrar**); haría falta EncryptedSharedPreferences/Keychain con un plugin de terceros.
  - **Límite de intentos en memoria**: no vale para varias instancias del backend (Redis o BD).
  - Sin SMTP configurado los enlaces solo salen por el log, así que `EXIGIR_EMAIL_VERIFICADO` sigue en `false` por defecto.
  - Sin probar: cambiar la contraseña estando dentro, cerrar sesión en todos los dispositivos a mano, borrar la cuenta y 2FA.
- Frontend: `src/api.ts` es el único sitio que habla con el backend; añade `Authorization: Bearer` y, ante un 401, renueva con el refresh una sola vez (compartida entre peticiones simultáneas) y repite; si no puede, cierra la sesión (`alCaducarLaSesion`). Los endpoints públicos van por `publica()`/`autenticar()`: sin token y sin reintento de refresh. La sesión la guarda `auth/almacen.ts` bajo la clave `ligacomunio.sesion`: **`localStorage` en web y `@capacitor/preferences` en nativo** (`Capacitor.isNativePlatform()`). Como `Preferences` es asíncrono, mantiene una copia en memoria y `api.inicializarSesion()` (que `AuthProvider` espera antes de decidir si hay sesión) la carga al arrancar; `leerSesion`/`guardarSesion` siguen siendo sincrónicas. `auth/` tiene el contexto (`contexto.ts`, `useAuth`), `AuthProvider`, `AuthPage` (login, registro, "¿Has olvidado la contraseña?" y botón de reenvío cuando el login da 403), `VerificarEmailPage` y `RestablecerPage` (las dos rutas de los enlaces del correo, `/verificar-email?token=` y `/restablecer?token=`, **públicas**: en `App.tsx` van fuera de la ruta `Privado`, que es la que muestra `AuthPage` sin sesión) y `AvisoVerificacion` (banner dentro de la app mientras `usuario.emailVerified` sea false, con reenvío).
- La base de la API del frontend es `VITE_API_URL` (vacía en web, donde Vite proxifica `/api`; obligatoria en builds Capacitor).
- Los nombres de métodos propios están en castellano (`calcular`, `listar`, `buscar`); los métodos de Spring Data (`findBy...`) y los getters de Lombok no se pueden renombrar.
- **Simulación de partidos** (`simulacion/`): es la forma normal de que una jornada esté lista. `SimuladorDeJornada` (no transaccional) recorre los partidos de la jornada **sin estadísticas** (`MatchRepository.idsSinEstadisticas`) y `GuardadoSimulacion` guarda cada uno en su propia transacción; `SimuladorDePartido` es lógica pura y `Dados` el azar. Reglas que no hay que romper: (1) **nunca sobrescribe** estadísticas existentes, así se mezclan jornadas reales importadas con jornadas simuladas; (2) es **reproducible** y **no depende de la liga**: la semilla se construye con `app.simulacion.semilla` + ids de partido/equipo/jugador, nunca con el reloj, así que todas las ligas ven los mismos puntos y simular dos veces da lo mismo; (3) si el partido ya tiene **marcador real** (todos los de 2024/25 lo tienen) se respeta y solo se inventa quién marcó —los goles repartidos entre los jugadores suman exactamente el marcador—; (4) los puntos los pone el `ScoringService`, igual que con los datos reales: el simulador solo produce datos brutos. Alinea un 4-4-2 con los mejores por valor de mercado más un ruido del partido (rotación), hace 2-4 cambios, y los suplentes que no juegan no generan fila (como en la importación). Ignora `player.status`: ese estado viene del archivo de Biwenger de otra temporada y dejaría a algunos lesionados para siempre. Disparadores ADMIN: `POST /api/admin/simulate/matchdays/{jornada}?season=2024` y `.../simulate/season?season=2024&hasta=38`. No gasta cuota de ninguna API.
- **Ligas y juego** (`league/`, tablas de `V7`): una liga tiene dueño, código de unión de 8 caracteres, temporada (`app.league.season=2024`), `current_matchday` (0 = no empezada), ritmo (`matchday_interval_seconds`, 3 días por defecto, mínimo 10 s) y `next_advance_at`. Reglas en `app.league.*` (`LeagueProperties`): presupuesto 40 M, plantilla máx. 18, máx. 20 miembros, mercado de 10 jugadores, tope de oferta +20 %. Al crear o unirse (solo antes de la jornada 1) se reciben 11 jugadores **gratis y al azar con valor > 0** (1 POR, 4 DEF, 4 MED, 2 DEL, todos titulares, táctica 4-4-2). Un jugador solo tiene un dueño por liga (`UNIQUE(league_id, player_id)`).
- **Modalidades de reparto inicial** (`InitialSquadMode`, `V12`): quien crea la liga elige con qué se empieza y queda **guardado en la liga** (`league.initial_squad_mode`, `initial_budget`, `initial_squad_cap`), no solo se usa al crearla, porque `LeagueService.unirse` también llama a `incorporar` y quien se une después tiene que recibir el mismo trato. `ALEATORIO` = los 11 al azar de siempre; `SIN_JUGADORES` = plantilla vacía (todo se ficha en el mercado); `ALEATORIO_CON_TOPE` = 11 al azar cuya **suma de valores no pasa del tope** (30 M por defecto) con un presupuesto aparte (20 M por defecto). El presupuesto lo elige quien crea la liga en las tres modalidades (40 M por defecto); `app.league.initial-budget` pasa a ser solo el valor que se propone y el que manda para repartir es `league.initial_budget`. El tope **solo** se admite en `ALEATORIO_CON_TOPE`, donde es obligatorio: enviarlo en otra modalidad da 400 (no se ignora, para que nadie crea tener un tope que no se aplica) y la base de datos lo refuerza con `chk_league_squad_cap`. El sorteo vive en `SorteoDePlantilla` (lógica pura, probada sin BD): recorre los 11 puestos en orden aleatorio y antes de cada elección descuenta la *reserva* (lo mínimo que costarán los puestos que faltan) para no pasarse del tope ni quedarse a medias, y limita el gasto de cada puesto a una *cuota* al azar en torno a su parte proporcional, de modo que la plantilla acaba cerca del tope pero nunca sale la misma dos veces; si ni los 11 más baratos libres caben en el tope, 409 explicando cuánto suman. La modalidad **no se puede cambiar** después de crear la liga (no está en `PUT /api/leagues/{id}/options`): cambiarla a mitad daría repartos distintos a miembros distintos. Con `SIN_JUGADORES` la penalización de puestos vacíos sigue igual: quien no fiche llega a la jornada 1 con 11 huecos, es decir **−44 puntos**, y no cobra nada; es a propósito y el formulario de crear liga lo avisa.
- **Tácticas** (`Formation`): 4-3-3, 5-3-2, 4-4-2, 3-5-2. En BD se guarda el nombre (`F442`) y la API usa el código (`"4-4-2"`). Los titulares (`squad_player.starter`) deben ser 11 y encajar con la táctica; el resto es banquillo (no puntúa).
- **Mercado** (`MarketService`): puja al mercado (se resuelve al avanzar jornada: gana la más alta, a igual importe la primera; si el comprador ya no tiene fondos u hueco se anula y opta la siguiente) y oferta directa al dueño (la acepta o rechaza; aceptar traspasa al instante y caduca al avanzar). Importe entero en `[valor, valor×1,2]`. Vender al sistema es instantáneo por el valor del jugador. Los fichajes entran al banquillo.
- **Opciones de la liga, abonos y expulsiones** (`V9`; `LeagueService.cambiarOpciones/expulsar/abonos`, pestaña `Opciones.tsx`): `league.point_value` (100.000 € por punto por defecto) y `league.position_bonuses` (lista de importes por puesto, por defecto `3000000,2000000,1000000`, parseada por `PremiosPorPosicion`). Al puntuar una jornada (`MatchdayService.puntuar`) cada miembro cobra `puntos x valor del punto` + el premio de su puesto en esa jornada; los empates comparten puesto y premio y quien no suma puntos positivos no cobra. Se guarda en `member_matchday_score` (`position`, `points_payout`, `position_bonus`) y se suma al presupuesto. `PUT /api/leagues/{id}/options` (solo dueño; rige desde la siguiente jornada), `GET /api/leagues/{id}/payouts` (clasificación por abonos) y `DELETE /api/leagues/{id}/members/{memberId}` (solo dueño; no puede expulsarse a sí mismo; se borra el miembro y la BD borra en cascada plantilla, ofertas y puntuaciones, así que sus jugadores vuelven a estar libres). En `LigaIntegrationTest` `ligaDeAnaConBeto()` pone los abonos a 0 para que los presupuestos solo cambien por el mercado; `ligaConAbonosDeAnaConBeto()` conserva los de por defecto. El panel del dueño (avanzar jornada, ritmo) vive ahora en la pestaña Opciones.
- **Avance con simulación** (`league/AvanceDeJornada`): única puerta de entrada al avance. Si la jornada siguiente no está lista la **simula** (instantáneo, sin cuota) y después llama a `MatchdayService.avanzar`; no es transaccional a propósito. Lo usan `POST /api/leagues/{id}/advance` (dueño, `automatico=false`), el reloj `LeagueScheduler` y la confirmación del último miembro que faltaba (`automatico=true`). Antes esto importaba de API-Football y por eso el reloj no podía usarlo; al simular ya sí, y con `automatico=true` se comprueba `tocaAvanzar` **antes** de simular para no generar la jornada siguiente en cada ciclo del reloj. El frontend muestra avisos de lesionado/sancionado/duda (`EstadoJugador.tsx`, desde `player.status`) y "No jugó" si el jugador no tiene puntos en la última jornada puntuada (no hay datos de convocatoria previa al partido en el plan gratuito).
- **Avance de jornada** (`MatchdayService.avanzar`): resolver mercado → puntuar titulares con `player_match_stats.points` de esa jornada → refrescar mercado → programar la siguiente. Solo avanza si los partidos de la jornada están `FINALIZADO` y con estadísticas (importadas o simuladas); si no, 409 sin cambios. Al llegar a la última jornada la liga pasa a `FINALIZADA`. **Para probar rápido**: el dueño puede poner el ritmo a 10-30 s (`PATCH /api/leagues/{id}`) o avanzar a mano.
- **Modos de avance y confirmación de alineación** (`AdvanceMode`, `V11`): `league.advance_mode` es `POR_TIEMPO` (se juega al vencer `next_advance_at`) o `POR_CONFIRMACION` (se juega en cuanto **todos** confirman; `next_advance_at` pasa a ser la fecha límite y `matchday_interval_seconds` el plazo, así que no hay columna nueva para eso). `league_member.lineup_confirmed_matchday` guarda **para qué jornada** se ha confirmado y se compara con `current_matchday + 1`: al avanzar la liga, las confirmaciones caducan solas sin tener que borrarlas. `SquadService.alinear` pone ese campo a 0 (cambiar la alineación deshace la confirmación) y `SquadService.confirmar` lo fija y devuelve si ya están todos; `SquadController` dispara entonces el avance **fuera** de esa transacción, para no tener la liga bloqueada mientras se simulan los partidos. `MatchdayService.tocaAvanzar` es la condición común y `LeagueRepository.idsAvanzables` hace que el reloj repase también las ligas por confirmación aunque no haya vencido el plazo. Si no se pone alineación se juega con la de la jornada anterior (los `starter` persisten).
- **Puestos vacíos: −4 puntos** (`app.league.empty-slot-penalty`, `V11`): un puesto vacío es un titular que ya no está en la plantilla (vendido o traspasado). La alineación se juega igual con los que queden, pero `MatchdayService.puntuar` resta `empty-slot-penalty` por cada hueco (`11 − nº de titulares`), así que los puntos de la jornada **pueden ser negativos** y entonces no se cobra nada (la regla de «quien no suma puntos positivos no cobra» ya estaba). Se guarda en `member_matchday_score` (`empty_slots`, `empty_slot_penalty`, ya descontado de `points`) para poder explicarlo en la clasificación. No cuenta como hueco un titular que sí está en la plantilla pero no jugó: ese suma 0.
- **Concurrencia**: toda escritura sobre una liga empieza con `AccesoLiga.ligaConBloqueo/miembroConBloqueo` (`SELECT ... FOR UPDATE` sobre la fila de la liga) y el miembro se lee **después** del bloqueo. `MarketService.aceptar` usa `noRollbackFor` para que una oferta que ya no se puede cumplir quede `ANULADA`.
- **Tests de integración** (`IntegracionBase`, `LigaIntegrationTest`, `BackendApplicationTests`): Postgres real con Testcontainers (se omiten solos sin Docker). Dos trampas ya resueltas: Docker 29+ exige API ≥ 1.40 y Testcontainers 1.x usa la 1.32 (se fija `api.version=1.44` en `maven-surefire-plugin` del `pom.xml`), y `@DirtiesContext(AFTER_CLASS)` evita que una clase reutilice el contexto de otra apuntando a un contenedor ya parado (si no, la batería se cuelga esperando conexiones).
- **Frontend de ligas**: `react-router-dom`; rutas `/` (mis ligas), `/ligas/:id` (+ `plantilla`, `tactica`, `mercado`, `rivales`, `opciones`) y `/jugadores`. `LigaPage` carga la liga, muestra la cuenta atrás y comparte `{liga, recargar}` con las pestañas por contexto (`ligas/ayudas.ts`); las pestañas se remontan (`key={currentMatchday}`) al cambiar la jornada. Al añadir una dependencia npm hay que reconstruir con `docker compose up -d --build -V frontend` (el `-V` renueva el volumen anónimo de `node_modules`); **sin el `-V` el contenedor no ve el paquete nuevo** y Vite sirve el `index.html` igualmente (HTTP 200) pero el módulo falla y la página sale en blanco, así que no basta con comprobar el código HTTP de la raíz: hay que pedir los módulos (`/src/main.tsx`) o abrirla en el navegador.
- **Mis jugadores y Táctica son dos pestañas distintas**: `MiPlantilla.tsx` (ruta `plantilla`, pestaña «Jugadores») es solo la lista —valor, lo pagado, puntos de la jornada, titular o banquillo y vender—, y `Tacticas.tsx` (ruta `tactica`) es donde se decide quién juega. La táctica se dibuja con **CSS puro, sin imágenes ni librerías**: el césped son franjas de un degradado repetido y la línea de medio campo y el círculo son pseudoelementos de `.campo`; las cuatro líneas van de arriba abajo (`LINEAS = DELANTERO, CENTROCAMPISTA, DEFENSA, PORTERO`) y el número de puestos de cada una sale de la táctica elegida. Se puede arrastrar (HTML5 drag & drop) **y también tocar**: un toque elige al jugador y el siguiente lo coloca. Ese segundo camino no es un adorno: el arrastrar-y-soltar de HTML5 **no funciona en pantallas táctiles**, así que sin él la táctica no se podría usar desde el móvil. Un puesto solo acepta jugadores de su posición (si no, se explica por qué en vez de dejar guardar algo que el backend rechazaría con 400), soltar en un puesto ocupado **intercambia** a los dos, y cambiar de táctica conserva a quien encaja en la nueva y manda al banquillo al resto. Guardar solo se activa con los 11 puestos cubiertos, porque `SquadService.alinear` exige exactamente 11. El botón de confirmar alineación vive aquí.
- **Valores de mercado** (`valores/`): `POST /api/admin/import/values/biwenger` (ADMIN, multipart `file`) lee el JSON de `https://cf.biwenger.com/api/v2/competitions/la-liga/data?lang=es&score=5` guardado desde el navegador (`biwinger-laliga.json` en la raíz, ignorado por git; no se automatizan peticiones a Biwenger). `BiwengerParser` usa `data.players[].price` como valor (`fantasyPrice` es del modo fantasy y no se usa; `position` 1-4 = POR/DEF/MED/DEL, 5 = entrenador y se descarta). `ValueImportService` empareja por equipo + nombre (nombre completo → palabras del nombre corto → palabras del slug) y solo asigna si el resultado es único (desempate por posición); respaldo por nombre completo en otro equipo (fichajes). Empareja en dos pasadas (primero dentro del equipo; después, con lo que queda, fichajes por nombre completo o por nombre abreviado tipo `a-gorosabel` ~ `Andoni Gorosabel`, misma posición y único) y también guarda el estado (`injured`→LESIONADO, `sanctioned`→SANCIONADO, `doubt`→DUDA; `warned` cuenta como disponible). Devuelve un informe de cobertura. La última fuente se guarda en `external_value` (`V8`) y `ImportService.importarJornada` la **reaplica sola** (`ValueImportService.reaplicar`) tras crear jugadores nuevos, así que solo hay que subir el archivo otra vez para refrescar valores o estados. Los jugadores sin valor quedan fuera del juego, pero ya no se quedan sin él: tras importar las plantillas, `GuardadoImportacion.generarValoresQueFaltan` pone un valor generado a los que el archivo no cubra. Limitación que queda: el archivo es de 2026/27 y la temporada jugada es 2024/25, así que solo coinciden unos 15 equipos y el resto de precios son inventados (estables, pero no reales).
- **Tests de la simulación**: `simulacion/SimulacionIntegrationTest` (Testcontainers) cubre lo que importa del motor: una jornada sin estadísticas se simula y deja resultado y puntos, es reproducible, no sobrescribe lo importado, **cinco jornadas seguidas con cuatro usuarios** dejan puntos/abonos/clasificación coherentes, los puestos vacíos restan 4 cada uno y el modo por confirmación avanza al confirmar el último. Amplía el catálogo de `IntegracionBase` en su `@BeforeEach` porque ese catálogo solo da para tres plantillas y los dos equipos necesitan 11 jugadores cada uno para que la simulación los alinee.
